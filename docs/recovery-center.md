# 背包恢复中心 1.2.0

玩家通过 `/mwirecovery` 或聊天入口查看记录、预览完整物品并确认领取；使用原版箱子界面，无需新客户端模组。
只填主背包 36 格，不覆盖装备/现有物品，不丢弃溢出物品。装备和 Curios 物品需要手动穿戴，余量可分批领取。

## 来源和领取条件

| 来源 | 状态与处理 |
| --- | --- |
| TSD 已独占封存的死亡余量 | AVAILABLE；复活后在对应共享范围领取 |
| TSD 1.5.0 已持久封存的普通墓碑 | V2 交接为 AVAILABLE，再用同一套 WAL 事务归还；满包留余量 |
| 旧备份、缺少认证凭证的托管 | REVIEW；可以查看和申请核验，管理员核实去向后才能批准 |
| 已领完、已人工结案 | CLOSED；永久禁止重开，保留审计物品不代表剩余额度 |

不通过空背包、缺少钥匙或快照差额猜测丢失。TSD 仅核查来源明确关联的墓碑；独占托管不受另一场死亡的
墓碑或未加载钥匙位置影响。关联墓碑不明仍禁止领取，但记录、原因和核验入口保持可见。
世界/共享组不符、创造模式也可查看条件，返回正确范围后重新预览；不自动跨世界写背包。
缺失模组、未知组件或损坏记录保留原件，不能按已解析部分发放；其他正常来源仍可处理。

## 持久交接与一次性领取

V2 `captureGraveScope / depositGrave / claimGrave` 是明确的能力边界，V1 的旧转移后 checkpoint 不能替代 V2。
TSD 先保存并校验物理墓碑封存凭证，再交出来源；尚未交接的记录登录后重试，同编号不会重建物品额度。
MWI 等待该玩家待写任务完成，原子保存来源与 profile；领取时按版本、校验码、当前会话、共享范围和完整背包
做比较，在同一 WAL 中提交主背包和剩余额度，随后应用并保存/回读玩家档案。完成后 TSD 才移除墓碑。

确认丢失、重复点击、旧区块墓碑重新出现、来源里保留了历史物品，都不能重开 CLOSED。
WAL 已持久后失败会隔离该玩家并保留事务；重启重放以同一 profile/来源修订为准，不倒退为可再领状态。
完整 ItemStack 编码保留附魔、耐久、嵌套容器、能量、外部存储标识；标识保留不代表能恢复外部存储本体。
预览槽阻止取物、拖拽、快捷移动、数字键、丢弃、双击和创造复制，只有确认按钮可进入领取事务。

TSD 安全墓碑路径不执行原先自动穿戴、快捷栏重排、反向排序和转移前 RestoreInventoryEvent；依赖该事件的
第三方集成需另行验收。未装 MWI 的原普通墓碑路径不具备本协议的持久交接保证。

## 可靠提醒

来源记录作为待通知依据，`data/mwi/recovery_notices/` 独立保存发送、自动打开、主动查看回执。
登录、复活、切换世界、新交接及核验批准均可入队。按 UUID 寻找当前玩家实例，等待玩家存活、会话稳定、
AuthMe 认证完成后才通知；未安装 AuthMe 时不额外要求登录插件。只使用其[只读认证 API](https://github.com/AuthMe/AuthMeReloaded/blob/master/authme-core/src/main/java/fr/xephi/authme/api/v3/AuthMeApi.java)，不代替玩家登录。

已打开其他容器时延迟自动界面；每个通知周期最多自动打开一次，未主动查看时最多每五分钟提醒一次。
主动查看或确认后停止该周期提醒；核验批准形成新周期。回执写入成功后，重启仍能去重。
发送/打开与回执落盘之间崩溃时可能再次提示，但不会再次发物品；通知回执损坏不阻止有效来源领取。
消息发送、界面打开、玩家查看和物品入账是四个不同状态，不能混为恢复成功。

## 玩家与管理员命令

```text
/mwirecovery
/mwirecovery open <来源UUID>
/mwirecovery inspect <在线玩家> <来源UUID>
/mwirecovery approve <在线玩家> <来源UUID> <inspect核验码> <核验依据>
/mwirecovery close <在线玩家> <来源UUID> <inspect核验码> <结案依据>
/mwirecovery close-external <在线玩家> <来源UUID> <原始证据SHA256> <结案依据>
```

后三类核验命令需要 2 级权限；目标玩家必须在线且在记录对应世界、共享组和模式中。`approve` 仅开放
已核实来源的领取权，物品仍由玩家确认；空的异常证据、无法无损解析的物品不能批准。
管理员必须核对墓碑、掉落、背包、外部存储及既往人工补发，不能仅凭旧快照批准。
`close-external` 只为尚未建档的准确来源登记永久结案标记，不发物品；已有记录应 `inspect` 后 `close`。
已人工恢复的事故必须先补结案，不能重新导入补发。不要把来源 UUID 当成文件名或任意生成新编号。

MWI 历史 revision 恢复仅在涉及已有恢复来源的同一玩家、同一物品共享范围时被阻止，避免绕过领取凭证；
普通墓碑存档凭证、其他玩家、其他共享范围及非物品恢复不受此门禁影响。MWI 的缺失模组物品隔离和
missing-item restore 保持原有行为，不自动导入本中心。TSD 旧托管和备份入口在安装本版本 MWI 时只允许转入此中心；
TSD `BIND_PENDING` / `BOUND` 不允许回到旧发放路径。

## 配套升级、验证与回退

配套版本：TSD 1.5.0、MWI 1.2.0、Tombstone 9.4.8、Minecraft 1.21.1；配套 GameTest 使用 NeoForge 21.1.244，
Curios 9.5.1+1.21.1 为可选依赖。主路径按实际服务端的右键、死亡/复活、恢复菜单和管理员命令验收。

先在完整 Youer 整合包的隔离副本测试，再停服备份完整世界、playerdata、`data/mwi/`、
`data/tombstonedefender/`、Tombstone 存储和配置。两个 JAR 成对升级，保存哈希。历史已补发事故先核验结案。
本地 NeoForge GameTest 不代表真实客户端、Youer/AuthMe/其他插件组合、JVM 原生崩溃或断电验收。

`recovery_sources`、`recovery_operations`、`recovery_notices`、TSD `grave_claims` 都必须保留；
物品来源和已领凭证不得随普通 revision 清理。列表有 4096 条安全上限；TSD 待交接索引重建上限为 65536 个墓碑凭证，
超限需管理员处理索引，不能通过删除凭证解决。物品提交/回读同步执行，需在实际磁盘验收延迟。
Windows 目录 fsync 不可用，文件 force 与原子替换并不等于已验证断电耐久性。

旧版不理解 V2 物理墓碑封存，不能单独降级某个 JAR 后继续领取。回退应停服保留现场，核对升级后所有领取，
优先修复前进；如需整体回退，使用同一时刻的整服快照。不得只回滚玩家档案、profile 或删除来源凭证。

本地验证：`./gradlew check jar`；配套真实服务器测试命令见 TSD `docs/recovery-center.md`。
